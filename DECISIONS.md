# DECISIONS.md — технические решения PredictorLab

Живой журнал решений и зафиксированных противоречий ТЗ. Нумерация сквозная.

## D-01. Split-conformal своей реализации вместо MAPIE
ТЗ (5.7) допускает выбор. Выбрана собственная реализация:
интервалы регрессии через квантиль абсолютных остатков на калибровочном фолде,
множества классов через APS (Adaptive Prediction Sets, Romano et al.) — маргинальное покрытие ≥ α.
Причины: меньше тяжёлых зависимостей, полный контроль покрытия (проверяется тестом α±5 п.п. на holdout ≥ 2000 строк),
детерминированность. Нюанс: множества считаются по сырым (некалиброванным) вероятностям —
изотоническая калибровка «сплющивает» вероятности в ступеньки и квантиль APS вырождается (овер-покрытие 0.97+).
Калиброванные вероятности используются для порога/прибыли, сырые — для конформальных множеств.

## D-02. Контрфактуалы: собственный поиск (greedy + random restarts) вместо dice-ml
ТЗ (5.11) допускает выбор. Собственный поиск: жадные шаги по actionable-признакам,
отсортированные по стоимости на единицу изменения вероятности, плюс случайные
рестарты в допустимых границах; жёсткий таймаут CF_TIMEOUT_SEC.
Причины: dice-ml плохо дружит с калиброванными вероятностями и матрицами
стоимости в рублях; нужен полный контроль ограничений (direction, range, immutable).

## D-03. Переиспользование DataSearcher
sql_guard, PII-паттерны (email/телефон РФ/ИНН/СНИЛС/паспорт/карта), маскирование,
JWT-механика (access/refresh, httponly cookie + Bearer), паттерн init_db с дефолтным
админом из .env, архитектура коннекторов (base/registry/SQLAlchemy), nginx-конфиг с
SSE-локацией — скопированы из DataSearcher (MIT, тот же владелец) и адаптированы.
API-ключи pl_live_, RBAC-роли, обязательная смена пароля, JSON-логи в stdout —
написаны с нуля (в DataSearcher их нет).

## D-04. Зависимости: backend/requirements.txt, а не только pyproject
pyproject.toml — метаданные и canonical-список зависимостей; requirements.txt —
то, что реально ставит Docker и dev-окружение (проверенный путь DataSearcher,
быстрее сборка образа). Разночтений быть не должно: тест в CI/приёмке сверяет.

## D-05. Метаданные: SQLite + sync SQLAlchemy
Как в DataSearcher: self-hosted без внешних сервисов, WAL-режим, busy_timeout.
Ковровых миграций нет — create_all + лёгкие ALTER при апгрейдах (таблицы только
добавляются). При переходе на 2–5 млн строк пострадают только тяжёлые выборки —
они идут в DuckDB, не в SQLite.

## D-06. Прогресс обучения и фоновые задачи
Очередь на asyncio + ProcessPoolExecutor (без Redis, ТЗ §10). Обучение и batch
выполняются в subprocess, прогресс пишут в таблицу job_events (SQLite WAL),
SSE-эндпоинт тail-читает события. Отмена — кооперативная: флаг cancel_requested,
процесс проверяет его между итерациями Optuna и стадиями, сохраняет лучший результат.

## D-07. Режим quick — CatBoost с ранней остановкой
«Дефолтные гиперпараметры» CatBoost (1000 итераций) на 50k×50 на CPU не влезают
в бюджет 1–2 мин. Quick-пресет: iterations=QUICK_ITERATIONS (500), depth=6,
lr=0.1, early_stopping по калибровочному фолду. Зафиксировано в manifest.

## D-08. Артефакты и подпись
joblib для pipeline/conformal/ood. Загрузка — только из собственного storage/.
При заданном ARTIFACT_SIGNING_KEY каждый артефакт подписывается HMAC-SHA256,
манифест содержит подписи; при загрузке подпись проверяется. Импорт чужих моделей
возможен только при включённой подписи и не подписывается нашими ключами (v0.2 ТЗ).

## D-09. Шрифт Proto Mono
Лицензия Proto Mono не подтверждена как свободная → по ТЗ используется фолбэк-цепочка
из --font: Share Tech Mono (OFL, кладётся в репозиторий) → JetBrains Mono → Consolas → monospace.
Проверка лицензии перед подключением выполнена: Proto Mono не включаем.

## D-10. Прогноз временных рядов (v0.3) — прагматичная реализация
Тип задачи timeseries: лаги + rolling-статистики + (опционально) календарные признаки,
baseline naive/seasonal-naive, CatBoost по построенным признакам, рекурсивный
многошаговый прогноз, конформальные интервалы на горизонте. Это не state-of-the-art
прогнозист, а честный инструмент с интервалами и базой для сравнения — фиксируем
в Model Card как ограничение.

## D-11. TabPFN — опциональная зависимость
Кандидат TabPFN подключается только при TABPFN_ENABLED=true и установленном
пакете (pip install predictorlab[tabpfn]); строки ≤ 10k, признаки ≤ 500.
Лицензия TabPFN требует атрибуции — отражено в README. По умолчанию не ставится
(образ не тяжелеет).

## D-12. Конформальные множества при дисбалансе классов: гарантия односторонняя
Математический факт: при доле мажоритарного класса 94% любое множество, содержащее
класс 0, уже покрывает ≥ 94% строк — покрытие α=0.9 для prediction sets недостижимо «точно»,
только сверху. Тест приёмки проверяет для классификации одностороннюю гарантию (coverage ≥ α),
а допуск α±5 п.п. из ТЗ 13.2 проверяется на регрессии (интервалы), где он достижим.
Покрытие измеряется и публикуется в BENCHMARKS.md с пояснением.

## D-13. Типизация: числовые колонки не парсятся как даты
pandas to_datetime() интерпретирует маленькие целые (1–12) как наносекунды от 1970 года —
это превращало числовые признаки в константы «даты» и убивало сигнал (AUC 0.52 вместо 0.85).
Теперь datetime-парсинг применяется только к нечисловым колонкам, в значениях которых
есть разделители дат (проверка _date_like). Эпохи-в-числах пользователь переключает вручную.

## Противоречия ТЗ (фиксация по правилу §0.5)
Пока не обнаружены блокирующие. Тонкости трактуются единообразно:
1. §5.12 п.2 «top_reasons опционально и только для top-N рисковых» = §11.1 — при batch
   с include=reasons причины считаются только top-N рисковых строк (TOP_REASON_ROWS).
2. §13.2 «покрытие в пределах α±5 п.п.» достижимо для регрессионных интервалов; для
   классификационных множеств при сильном дисбалансе гарантируется только coverage ≥ α (см. D-12).
3. §5.4 «пересечение train/test → BLOCK» трактуется с учётом §5.2: для rolling-срезов одна
   сущность обязана попадать в несколько срезов, а «спящие» сущности дают одинаковые строки.
   Для out-of-time сплитов пересечение сущностей и совпадающие строки понижаются до WARN
   (валидация остаётся честной по времени); BLOCK — только для случайных сплитов.
